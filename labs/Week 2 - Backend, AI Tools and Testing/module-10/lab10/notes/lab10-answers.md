### Concepts to Discuss
1. **Difference between a Copilot inline completion and a Copilot Chat request—when is each better?**\
Chat request is better when you need multi-method classes with actual rules attached. For example, `CustomerService` in this lab. Inline completions are better for finishing a few obvious lines of code, but nothing too extensive.
2. **Why prompt specificity (fields, types, rules) changes enterprise Java output quality vs a vague comment?**\
A vague prompt allows Copilot to guess a structure for whatever it is you're making. Being specific and naming exact fields, types, and rules helps ensure that the output matches your actual requirements.
3. **What is the “trust boundary” between an AI suggestion and code allowed to touch real customer data?**\
The code outputted by AI should be seen as unreviewed until it is actually gone over by a human. Until this happens and the code is verified manually, real customer data should never touch code or prompts.
4. **Which business rule protects integrity in Customer (fixed CustomerStatus enum vs free-text String)?**\
The fixed `CustomerStatus` enum makes sure only valid statuses can be assigned to a customer. This avoids errors from input mismatch, typos, etc.
5. **What happens if Copilot suggests a class/annotation/library not on this project’s classpath?**\
You should reject it. If it is not on the classpath, it will not compile. You should reprompt Copilot to use only the libraries that are actually available in your project.
6. **Why must every accepted suggestion be reviewed line-by-line, not only “does it compile”?**\
Compiling only means that syntax is correct, not that the code is correct or meets the business rules. You must review line-by-line to ensure that the logic, rules, and structure are all correct and appropriate for the application.
7. **What is the risk of pasting real customer data or credentials into Copilot Chat?**\
Pasting real customer data into Copilot Chat means it is being passed to a third-party and at risk of being leaked. You should never paste real customer data or credentials into any AI tool.
8. **How does license/provenance risk apply to a multi-line AI block, and what if it looks copied from a known OSS project?**\
If it looks copied you shouldn't accept it blindly. You should at least rewrite it in your own words or structure to avoid potential licensing issues. 
9. **Why is Copilot not a runtime dependency of customer-service?**\
It only is used before runtime when designing in the IDE. The code generated by Copilot is just like any other code that somebody has written, Copilot code will never actually be part of the runtime dependencies of the application.
10. **How will Lab 11 reuse today’s review discipline when generating tests?**\
The same reviewing process applies to lab 11 and AI-generated tests. Even if it compiles, it doesn't mean it is correct. Generating tests is especially important to be accurate with.

### Security and Production Review
1. **Which parts of a Copilot prompt are untrusted from the model’s perspective, and which are trusted (your business rules)?**\
The model will almost always assume everything in the prompt is untrusted. Only business rules we've stated in the prompt are trusted, but not anything the model comes up with itself.
2. **Where is human review formally enforced before AI code reaches the shared repo?**\
The mandatory review-log entries such as `lab10-003` enforce it. Nothing will reach the repo without one.
3. **Which values must never appear in Chat, even as examples?**\
Any real customer data, PII, passwords, or credentials should never be passed to any AI tool. Any sensitive, personally identifying data must never appear in a chat.
4. **What can be safely regenerated if rejected, and what must a human write from scratch?**\
Boilerplate code like getters and setters are okay to be regenerated if rejected. Any other code pertaining to the actual business rules and their exact wording must be written manually.
5. **What if an AI-suggested dependency only fails in CI mvn compile, not locally?**\
This usually means a version mismatch between the Maven repo cache and a clean CI checkout. Checking the dependency tree should be the next step.
6. **What would a tech lead audit to confirm AI-assisted code met the same bar as hand-written code?**\
They would audit the review log and the code style to see if it matches the rest of the codebase. Even if it compiles, it doesn't mean it is correct.
7. **Which licensing/IP concern applies to large verbatim-looking suggestions, and how do you mitigate it?**\
They apply to large verbatim-looking blocks. You can mitigate this by rewriting chunks in your own wording / structure.
8. **How do you keep an audit trail of what a human verified vs what the AI produced?**\
The review-log entries should keep track of this. They track the prompt used, the output summary, accept/reject decision, and reason.
